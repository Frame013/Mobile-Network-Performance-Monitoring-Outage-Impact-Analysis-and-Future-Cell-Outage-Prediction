# Mobile Network Performance Monitoring, Outage Impact Analysis, and Future Cell Outage Prediction

Course project (Introduction to Computer Programming with Python).
**Team:** Nyo Lae Hnin · Sunisa Aobaom

We study what happens when a mobile cell goes down: how much service is lost, how the load moves to neighboring cells, and whether network KPIs can warn about an outage 12 hours in advance.

> **Important:** all data in this project are **synthetic**. They were generated by our own Python scripts (fixed seed 42) to imitate a Ugandan 2G–5G network. They are not real operator records, and the results describe the synthetic data, not a real network.

## Research questions

| # | Question | Status |
|---|---|---|
| RQ1 | How large is the impact of outages on the network (downtime, availability by technology)? | Done |
| RQ2 | How are neighboring cells affected while a cell is down? | Done |
| RQ3 | Can the KPIs of the last 6 hours predict a new outage in the next 12 hours, better than simple warning rules? | Done: negative result, explained |
| RQ3-extra | Do neighbor and same-site outage features improve prediction? | Done: no improvement |

## Key results (main notebook, current dataset)

- **Data:** 6,000 sites, 22,900 cells, 133.9 million rows (Jan 2024 – Dec 2025, one KPI record every 3 h), 25,859 outages.
- **RQ1:** network availability **99.9855 %**, 58,170 cell-hours of recovered downtime; 2G has the lowest availability and 5G the highest.
- **RQ2:** while a cell is down, its neighbors show higher load, users, latency and packet loss in **63–70 %** of 2,938 outage–neighbor pairs (difference-in-differences against the same hours 7 days earlier).
- **RQ3:** outages are rare (**0.077 %** of rows). Every model and rule scores about **1.0× random guessing** on PR-AUC:

  | Model | Temporal test (Mar/Jul/Nov 2025) | Unseen-site test (2,000 sites) |
  |---|---|---|
  | Rule: Alarm_Count ≥ 1 | 1.02× | 1.00× |
  | Logistic Regression | 1.09× | 1.11× |
  | Random Forest | 1.04× | 1.08× |

- **Why prediction fails:** in the 12 h before an outage, KPIs are no different from the same hours a week earlier (Wilcoxon p = 0.40–0.97). In the original generator script (`scripts/generate_dataset2_v1_original.py`), outage risk depends only on time of day, season and technology — the KPIs are never used — and the current dataset shows the same lack of signal. As a **positive control**, we added artificial warning signs to test data (`scripts/generate_dataset2_v2_signal.py`): the same pipeline then scored 13.5× (25 % of outages with signs) and 52× (50 %) better than random. So the method works when a signal exists.

## How to run

1. Put the data files in one folder (see `data/README.md`).
2. **`notebooks/01_main_analysis.ipynb`** — edit the folder path in Section 5.1 (`PROJECT_DIR`) and the paths in Sections 5.3–5.5, then run the cells in order (Kernel → Restart & Run All).
   - The feature step (5.4) writes a large intermediate file (~62 GB). Make sure the drive has enough free space.
   - Section 5.9 (neighbor and shared-site features) reuses variables from Sections 5.2 and 5.5, so run it after them.
3. **`notebooks/02_next_steps_rq2_rq3.ipynb`** — edit the paths in Step 0 and run Steps 0–6. It converts the CSV to Parquet once (a few minutes) and then runs in minutes.

## Methods (short)

- **Target:** `Outage_Next_12h = 1` if a new outage starts in the next 12 hours, built from event times only (no future leakage).
- **Features:** current KPIs plus 6-hour lags, averages and trends, computed on disk with DuckDB; technology and region.
- **Split:** train on 2024 (seen sites only); validation Feb/Jun/Oct 2025; temporal test Mar/Jul/Nov 2025; plus an unseen-site test on 2,000 randomly held-out sites.
- **Models:** operational rules (utilization / alarm), Logistic Regression, Random Forest; thresholds tuned on validation.
- **Metrics:** precision, recall, F1, PR-AUC compared with random guessing, and false alarms per site-day (accuracy is not used because outages are rare).

## Limitations

- Synthetic data: every pattern found partly reflects the generator's rules.
- No outage-cause labels (gradual vs sudden failures cannot be separated).
- KPIs are recorded only every 3 hours, so short outages are hard to observe.
- Validation and temporal-test sets use a 5 % sample of seen-site cells to limit memory use; the unseen-site test uses all rows of its sites.
